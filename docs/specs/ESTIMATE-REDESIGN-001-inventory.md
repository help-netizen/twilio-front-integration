# ESTIMATE-REDESIGN-001 — current-state inventory

**Research date:** 2026-08-14
**Scope:** current shipped code only; no proposed visual design or UI implementation.
**Precedent:** the ten approved invoice decisions are binding for the eventual estimate rebuild (`docs/specs/INVOICE-REDESIGN-001.md:15-42`), and the adopted type canon is 32/20/15 with only 500/600 weight and semantic colour below a section heading (`docs/specs/TYPE-CANON-001.md:21-40`).

## Reading conventions

- **Level 1** is a page or entity panel/embedded entity section. **Level 2** is an overlay opened from it. **Level 3** is an overlay, picker, or popover opened from level 2. The same reusable component can therefore have two levels depending on its opener.
- “Absent” means the reviewed code has no state or affordance; it does not infer intended behavior.
- API permissions below are the route middleware requirements, not what the frontend happens to show. All estimate API routes are mounted behind `authenticate` and `requireCompanyAccess` (`src/server.js:247-258`), and the estimate router obtains tenant context only from `req.companyFilter?.company_id` (`backend/src/routes/estimates.js:17-24`).
- “Delete” in the current estimates API is an archive alias, not a hard delete (`backend/src/routes/estimates.js:303-320`).

## 2. Estimate-specific behavior that invoices do not have

### 2.1 Lifecycle, approval, decline, and expiry

- The current canonical statuses are exactly `draft`, `sent`, `viewed`, `approved`, and `declined`, in both the frontend type and the database constraint (`frontend/src/services/estimatesApi.ts:29-33`; `backend/db/migrations/082_pf002_r2_estimates_refresh.sql:6-26`). The original migration once allowed `accepted`, `expired`, and `converted`, but the later canonical constraint removed them (`backend/db/migrations/053_create_estimates.sql:6-15`; `backend/db/migrations/082_pf002_r2_estimates_refresh.sql:6-26`).
- There is no estimate SCXML/FSM. The state machine is effectively the DB `CHECK` plus unguarded service methods: Send always writes `sent`, Approve writes `approved`, and Decline writes `declined` without validating the prior status (`backend/src/services/estimatesService.js:574-737`; `backend/src/services/estimatesService.js:740-886`). Consequently, an approved estimate can be resent back to `sent`, and draft/declined records can be approved; these are current-code behaviors, not proposed rules.
- Any update to a non-draft estimate resets it to `draft`; linking a job also resets a non-draft estimate (`backend/src/services/estimatesService.js:267-340`; `backend/src/services/estimatesService.js:888-930`). Item mutations use the same reset-after-edit behavior (`backend/src/services/estimatesService.js:390-417`).
- The shipped public view logs view activity but does not set status to `viewed`; no current service writes `viewed` (`backend/src/services/estimatesService.js:1193-1236`). The UI can display/filter a status that the shipped customer flow never reaches (`frontend/src/pages/EstimatesPage.tsx:84-129`; `frontend/src/pages/EstimatesPage.tsx:163-174`).
- `valid_until` exists in the original table and in TypeScript input types, but current create/update allowed-column lists omit it, no estimate UI edits/displays it, and the current constraint has no `expired` status (`backend/db/migrations/053_create_estimates.sql:24-30`; `frontend/src/services/estimatesApi.ts:58-64`; `frontend/src/services/estimatesApi.ts:122-143`; `backend/src/db/estimatesQueries.js:270-360`; `backend/db/migrations/082_pf002_r2_estimates_refresh.sql:6-26`). **Expiry behavior is absent.**

### 2.2 Estimate → job and estimate → invoice

- **Estimate → job conversion is absent.** Current estimate behavior only links an existing job by numeric ID (`frontend/src/components/estimates/EstimateDetailPanel.tsx:321-324`; `backend/src/routes/estimates.js:456-478`). Link Job renumbers/relates the estimate and resets it to draft; it does not create a job (`backend/src/services/estimatesService.js:888-930`).
- Lead → Job conversion does create/reuse a job and update the lead, but its transaction contains no estimate-link operation (`backend/src/services/leadConversionService.js:28-155`). Therefore it is a separate lead lifecycle, not estimate conversion.
- **Estimate → invoice exists.** It is approved-only and idempotently returns the already-linked invoice (`backend/src/services/estimatesService.js:933-963`). It copies entity links, summary/notes, internal note, order list, tax/discount/currency/due data and all items, records events, then returns the invoice (`backend/src/services/estimatesService.js:967-1092`). The transaction is company-scoped (`backend/src/services/estimatesService.js:1095-1123`).
- The detail panel exposes Create Invoice for an approved estimate and then navigates to `/invoices?openId=<id>` (`frontend/src/components/estimates/EstimateDetailPanel.tsx:285-298`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:343-355`). The route requires `invoices.create`, while the destination page separately requires `invoices.view` (`backend/src/routes/estimates.js:434-453`; `frontend/src/App.tsx:149-150`).

### 2.3 Public customer experience

- The active `/e/:token` experience is view/PDF-only; it cannot approve, decline, sign, pay, or add a comment (`frontend/src/pages/PublicEstimateViewPage.tsx:5-10`; `frontend/src/pages/PublicEstimateViewPage.tsx:68-110`). A view logs an activity but does not transition status (`backend/src/services/estimatesService.js:1193-1236`).
- An older `/api/portal` backend has document accept/decline endpoints and client-signature enforcement, but public portal login is disabled by default and there is no portal frontend in the reviewed frontend tree (`backend/src/routes/portal.js:17-27`; `backend/src/routes/portal.js:203-270`; `backend/src/services/portalService.js:137-269`). Those capabilities exist only in dormant backend portal code; the active customer page is read-only (`frontend/src/pages/PublicEstimateViewPage.tsx:5-10`; `backend/src/routes/portal.js:17-27`; `backend/src/routes/portal.js:203-270`).

## 3. Broken or dangerous current behavior

### 3.1 The three invoice-pass bugs

1. **Unhydrated edit saving `items: []`: present.** Standalone row Edit passes the list-row object directly (`frontend/src/pages/EstimatesPage.tsx:66-69`; `frontend/src/pages/EstimatesPage.tsx:175-183`). The editor initializes missing items to `[]` and always sends a full `items` replacement (`frontend/src/components/estimates/EstimateEditorDialog.tsx:91-110`; `frontend/src/components/estimates/EstimateEditorDialog.tsx:288-315`). Because list queries do not hydrate items, saving can delete all existing lines (`backend/src/db/estimatesQueries.js:95-125`; `backend/src/services/estimatesService.js:267-340`).
2. **Wrong-recipient row Send: present.** The row stores `sendEstimateId`, but the dialog recipient comes from the unrelated `page.selectedEstimate` and omits phone/name; target ID and recipient can therefore represent different estimates (`frontend/src/pages/EstimatesPage.tsx:184-188`; `frontend/src/pages/EstimatesPage.tsx:237-245`).
3. **`page` ↔ `offset` pagination bug: absent.** The client explicitly calculates `offset = (page - 1) * limit` and does not send `page` (`frontend/src/services/estimatesApi.ts:285-304`).

### 3.2 Destructive and state-safety gaps

- Standalone/detail Archive executes without confirmation; `DELETE` also only archives, so there is no hard-delete estimate confirmation path (`frontend/src/pages/EstimatesPage.tsx:175-193`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:745-747`; `backend/src/routes/estimates.js:303-320`).
- Detail item removal calls the DELETE route immediately with no confirmation (`frontend/src/components/estimates/EstimateDetailPanel.tsx:255-261`). Editor item and order-list removal are local but immediate and have no confirmation/undo (`frontend/src/components/estimates/EstimateEditorDialog.tsx:481-485`; `frontend/src/components/estimates/OrderListSection.tsx:34-96`).
- Editor, summary, item, send, and decline close without dirty confirmation (`frontend/src/components/estimates/EstimateEditorDialog.tsx:324-350`; `frontend/src/components/estimates/EstimateSummaryDialog.tsx:25-56`; `frontend/src/components/estimates/EstimateItemDialog.tsx:26-41`; `frontend/src/components/estimates/EstimateSendDialog.tsx:176-260`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:798-807`).
- Lifecycle services do not validate allowed prior states; Send can demote approved to sent, Approve can approve draft/declined, and Decline can decline approved/draft (`backend/src/services/estimatesService.js:574-886`).
- Public tokens have no state/archive/expiry guard or revoke path, so a leaked token remains a durable read credential (`backend/src/db/estimatesQueries.js:661-690`; `backend/src/services/estimatesService.js:1163-1190`).

### 3.3 Permission and failure-path gaps

- A view-only user can see standalone Edit/Archive/Restore/Send, and detail Edit, item changes, Link Job, Archive/Restore, Approve/Decline, and Create Invoice even when the matching backend permission will reject the action (`frontend/src/pages/EstimatesPage.tsx:175-193`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:74-80`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:343-355`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:717-768`).

- Email send readiness is probed through `messages.send`, not `estimates.send`; an estimate sender lacking message permission sees Email as disconnected. - Price Book read failures—including a missing `price_book.view`—silently look like an empty catalog (`frontend/src/components/estimates/ItemPresetSearchCombobox.tsx:81-131`). - AI draft generation requires only `estimates.create` but reads the company Price Book digest regardless of `price_book.view`; the route computes `canManagePriceBook`, but the called service ignores that argument (`backend/src/routes/estimates.js:107-124`; `backend/src/services/aiEstimateService.js:764-787`). - Detail mounts `TaskStack` without checking `tasks.view`; its task hook always requests the entity list and silently swallows a `403`, so missing task permission looks like no tasks (`frontend/src/components/estimates/EstimateDetailPanel.tsx:646-653`; `frontend/src/components/tasks/TaskStack.tsx:25-33`; `frontend/src/components/tasks/useEntityTasks.ts:9-18`). The frontend also grants task actions only to assignee/manager, while the backend additionally permits the author, so an authorized author can lose the UI controls (`frontend/src/components/tasks/TaskStack.tsx:40-40`; `backend/src/routes/tasks.js:70-73`).
- Detail conversion checks neither `invoices.create` nor destination `invoices.view`; a custom role can be shown a CTA that 403s, or create an invoice it cannot then open (`frontend/src/components/estimates/EstimateDetailPanel.tsx:74-80`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:285-298`; `frontend/src/App.tsx:149-150`).

### 3.4 Tenancy audit

- Core authenticated list/detail/create/update/item/action queries are company-scoped, and the router uses `req.companyFilter`, not `req.companyId` (`backend/src/routes/estimates.js:17-24`; `backend/src/db/estimatesQueries.js:27-65`; `backend/src/db/estimatesQueries.js:95-181`; `backend/src/db/estimatesQueries.js:270-360`). Public token reads intentionally use the random token as the credential (`backend/src/routes/public-estimates.js:11-25`).
- Audit/write user IDs come from `req.user.crmUser.id`, not the authentication subject, and the create/update/action routes pass that value into the service (`backend/src/routes/estimates.js:22-24`; `backend/src/routes/estimates.js:71-84`; `backend/src/routes/estimates.js:234-249`). The reviewed estimate router therefore does not carry the known `req.user.sub` foreign-key failure.
- Revisions and events tables have no `company_id`; the service first performs a company-scoped parent estimate lookup, then the history queries filter only by `estimate_id` (`backend/db/migrations/055_create_estimate_revisions.sql:6-16`; `backend/db/migrations/056_create_estimate_events.sql:6-18`; `backend/src/services/estimatesService.js:1130-1140`; `backend/src/db/estimatesQueries.js:621-654`). This currently prevents a foreign parent read, but it violates the project’s “every SQL query filters by company” invariant and is fragile.
- Link Job returns a `400` validation error when the supplied job is missing/foreign rather than the tenancy canon’s required foreign-ID `404` (`backend/src/services/estimatesService.js:888-895`; `docs/specs/TENANCY-RBAC-CANON.md:14-20`).

### 3.5 Other correctness/reliability defects

- Detail’s auto-save helper silently drops any second mutation while a prior save is in flight; the explicit Save waits 150 ms, refreshes, and always toasts “All changes saved,” even if a dropped/failed blur save occurred (`frontend/src/components/estimates/EstimateDetailPanel.tsx:267-281`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:326-338`).
- Summary and item dialogs close before their async parent saves complete, so a failed save can leave the editor dismissed (`frontend/src/components/estimates/EstimateSummaryDialog.tsx:25-56`; `frontend/src/components/estimates/EstimateItemDialog.tsx:26-39`).
- Standalone list fetch failure has no rendered error state (initial failure looks empty; later failure can show stale rows), and detail hydration failure is silent (`frontend/src/hooks/useEstimates.ts:44-67`; `frontend/src/pages/EstimatesPage.tsx:131-143`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:90-98`). Job and Lead detail-open handlers have `finally` but no catch/error state, so a failed detail/event request rejects without a surface message (`frontend/src/components/jobs/JobFinancialsTab.tsx:126-139`; `frontend/src/components/leads/LeadFinancialsTab.tsx:57-70`).

## 4. Data and plumbing notes for a rebuild

### 4.1 Frontend data layer

- `frontend/src/services/estimatesApi.ts:29-143` defines the shared `Estimate`, item, create, and list contracts; `frontend/src/services/estimatesApi.ts:285-411` exposes list/detail/CRUD/send/public/approval/link/item/event/revision/convert calls.
- The client exposes revisions, but no estimate screen invokes that function; detail History renders only its supplied event array (`frontend/src/services/estimatesApi.ts:402-411`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:700-712`). Attachment GET/POST routes are `501` stubs and no estimate surface exposes an attachment action (`backend/src/routes/estimates.js:593-603`).
- `useEstimates` owns the standalone list, selected detail, events, loading/error, and action refreshes (`frontend/src/hooks/useEstimates.ts:33-166`). Selecting a row fetches detail first and events second while keeping `detailLoading` true; if the event request fails, the fetched detail still renders after the catch but `events` is not cleared, so history from the previous selection can remain (`frontend/src/hooks/useEstimates.ts:73-92`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:307-313`).
- Job uses `useJobFinancials` and performs a separate full estimate + event hydration on open (`frontend/src/hooks/useJobFinancials.ts:135-183`; `frontend/src/components/jobs/JobFinancialsTab.tsx:126-139`). Lead’s list hook loads list rows, while its component separately fetches detail/events on selection (`frontend/src/hooks/useLeadFinancials.ts:34-65`; `frontend/src/components/leads/LeadFinancialsTab.tsx:57-70`).

### 4.2 List row versus detail payload

- List SQL returns `e.*` plus contact email/phone, job number/status, and linked invoice metadata; it does **not** join/hydrate `estimate_items` (`backend/src/db/estimatesQueries.js:95-125`).
- Detail SQL returns the company-scoped estimate plus contact, job, service-address, billing-address, lead, and invoice metadata (`backend/src/db/estimatesQueries.js:128-181`). The service then separately loads and attaches `items` (`backend/src/services/estimatesService.js:129-140`).
- Both list and detail rows receive derived payment values after querying the job payment pool (`backend/src/db/estimatesQueries.js:122-125`; `backend/src/db/estimatesQueries.js:179-181`; `backend/src/db/documentPaymentQueries.js:258-279`).

### 4.3 Hydration requirements

- Any edit that can replace `items` must begin from `fetchEstimate(id)`, never a list row. Standalone Edit currently violates this; standalone row-open, Job, and Lead hydrate before opening detail (`frontend/src/pages/EstimatesPage.tsx:66-69`; `frontend/src/hooks/useEstimates.ts:73-87`; `frontend/src/components/jobs/JobFinancialsTab.tsx:126-139`; `frontend/src/components/leads/LeadFinancialsTab.tsx:57-70`).
- Send prefills must be derived from the same hydrated/list object whose ID is submitted. Standalone currently stores only an ID and reads recipient data from separate selection state (`frontend/src/pages/EstimatesPage.tsx:46-53`; `frontend/src/pages/EstimatesPage.tsx:184-188`; `frontend/src/pages/EstimatesPage.tsx:237-245`).
- Detail already has defensive hydration when `items` is absent, but failure is silent and the editor callback may still receive partial data; a rebuild needs an explicit hydrated-detail contract/state (`frontend/src/components/estimates/EstimateDetailPanel.tsx:81-98`; `frontend/src/components/estimates/EstimateDetailPanel.tsx:751-761`).
- Create requires a `lead_id` or `job_id`; there is no contact-only create context despite contact fields existing on result objects (`backend/src/services/estimatesService.js:169-214`; `backend/src/services/estimatesService.js:222-264`). This is why Job/Lead are the functional create entry points and the standalone page has no viable context selector today.
