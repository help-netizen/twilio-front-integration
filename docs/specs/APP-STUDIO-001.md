# APP-STUDIO-001 — конструктор приложений маркетплейса (чат-билдер)

Статус: **АРХИТЕКТУРА НА СОГЛАСОВАНИИ** (кода нет). Автор: Claude (тимлид/архитектор).
Источник: запрос владельца 2026-07-31 — «раздел конструктор приложения… переписка с ботом,
чтобы создать своё приложение для маркетплейса; он может использовать только MCP и публичный API».

---

## 1. Что такое «приложение» (главное решение)

**Приложение = декларативный манифест, а не код.** Пользователь не пишет и не запускает код;
он собирает в чате объект, который наш рантайм умеет исполнять. Это единственная трактовка,
совместимая с ограничением владельца «только MCP и публичный API», и единственная безопасная:
чужой код в нашем контуре не исполняется никогда.

Манифест приложения состоит из четырёх частей:

1. **Профиль** (витрина): `app_key`, имя, логотип, категория, короткое описание для карточки,
   **человекочитаемое длинное описание** (что делает, кому нужно, что включает), контакт поддержки.
   Ложится на существующую таблицу `marketplace_apps` (все эти поля там уже есть).
2. **Набор команд (MCP-tools)** — allowlist из НАШЕГО каталога инструментов
   (`agentSkillsMcpRegistry` + `chatgptMcpRead/WriteService`). Пользователь не изобретает команды,
   он выбирает из существующих и даёт им человеческое имя/описание в контексте своего приложения.
   Это и есть «перечень команд, доступных для MCP».
3. **Агент** (необязательно): персона/системный промпт, триггер (по событию или по запросу),
   привязка модели — **наша платформенная** (токены тарифицируются) или **своя** (BYO-ключ,
   токены не тарифицируются).
4. **Доступность MCP**: `company` (только своя компания) либо `public` (любой тенант, который
   установит приложение). Значение выводится из режима публикации, отдельной ручки нет.

## 2. Жизненный цикл и версии

```
draft → submitted → in_review → published
                            └→ rejected → draft (с причиной от модератора)
```

- Правка **опубликованного** приложения создаёт новую **версию**: в маркетплейсе продолжает
  работать последняя одобренная, новая уходит на модерацию. Установки не ломаются.
- Внутреннее (`company`) приложение публикации не требует — работает сразу после сохранения,
  но **тоже проходит проверку scope** (см. §5), потому что тянет данные компании.
- Модерация — вкладка супер-админа (прецедент: очередь модерации отзывов, MARKETPLACE-RATINGS-001).

## 3. Данные (новые таблицы)

| Таблица | Назначение |
|---|---|
| `app_builds` | версия манифеста: `app_id`, `version`, `company_id`, `status`, `manifest_json`, `submitted_at/by`, `reviewed_at/by`, `review_note` |
| `app_build_tools` | выбранные MCP-команды версии: `build_id`, `tool_key`, `display_name`, `description`, `scope_keys[]` |
| `app_build_chats` | чат билдера: `app_id` (nullable для «нового»), `company_id`, `title`, `created_by` |
| `app_build_messages` | **полный лог переписки с LLM**: `chat_id`, `role`, `content`, `model`, `tokens_in/out`, `tool_calls_json`, `created_at` |
| `app_llm_credentials` | BYO-ключи: `company_id`, `app_id`, `provider`, `encrypted_key`, `model` |

Маркетплейс-витрина остаётся на `marketplace_apps` / `marketplace_installations` — конструктор
лишь порождает и обновляет там записи через одобренные версии.

## 4. Биллинг

- **Внутреннее приложение (company-only): $38/мес за компанию** — отдельная позиция подписки
  (`billingService`, план-аддон). Считается по факту наличия хотя бы одного активного внутреннего
  приложения; несколько приложений — обсуждается (см. §8, вопрос 1).
- **Токены LLM** — сверх подписки, метрятся на приложение (`app_build_messages.tokens_*` + рантайм
  агента) и списываются с кошелька (`walletService`, механика уже есть).
- **BYO-модель**: приложение привязано к ключу компании → **токены не тарифицируются**, платится
  только подписка. Ключ хранится зашифрованным, не показывается обратно, доступен только рантайму.
- Публичные приложения: модель монетизации — **вопрос владельца** (§8, вопрос 2).

## 5. Безопасность (решения, не обсуждаются)

1. **Приложение не может получить больше прав, чем есть у устанавливающей компании.** MCP-вызов
   исполняется в контексте установщика с его RBAC; allowlist — это потолок, а не выдача прав.
2. **Автор публичного приложения не видит данные установщиков.** Никогда. Никакого «телеметрийного»
   доступа к чужим тенантам — только агрегированная статистика установок.
3. **Allowlist валидируется на сервере** против каталога MCP; чат-бот не может «придумать» команду —
   он лишь предлагает существующие, финальную запись делает бэкенд по ключам каталога.
4. **Описания приложений — недоверенный текст**: та же трёхслойная модерация, что у отзывов
   (ссылки → hard-reject, инъекция/мат → на ручную проверку, fail-closed при сбое проверки).
5. **Публичный MCP-эндпоинт** приложения — под существующей аутентификацией
   (`agentSkillsMcpPublicAuth`), с company-scoping на каждом запросе и rate-limit.
6. Строить приложения может **только tenant_admin** (приложение = доступ к данным компании).

## 6. UX

**Вход:** существующий виджет обратной связи получает второй раздел — **App Studio**.
- Слева — список приложений компании (каждое = отдельный чат) + кнопка **New app**.
- В центре — переписка с ботом-билдером; вся история сохраняется и видна при следующем открытии.
- Справа — **живой профиль приложения** (шторка по FORM-CANON): логотип, имя, описания, список
  команд. Заполняется по мере разговора, редактируется руками, внизу — `Save draft` /
  `Submit for review`.
- Статус версии — плашка вверху чата: Draft / In review / Published / Rejected + причина.

**Супер-админ:** новая вкладка **Apps** — очередь модерации: заявка, дифф к предыдущей версии,
запрошенные MCP-команды с их scope, **полная переписка билдера**, кнопки Approve / Reject (+ причина).

## 7. Порядок работ (предложение)

- **T1** — данные + манифест-модель + серверная валидация allowlist (без UI).
- **T2** — чат-билдер: хранение чатов/сообщений, бот с каталогом команд, лог токенов.
- **T3** — UI App Studio в виджете (список чатов, профиль-шторка, статусы).
- **T4** — модерация у супер-админа (очередь, дифф, approve/reject).
- **T5** — MCP-эндпоинт приложения (company/public) + rate-limit + аудит вызовов.
- **T6** — биллинг: аддон $38/мес, метрика токенов, BYO-ключи.

## 8. Открытые вопросы (решает владелец)

1. **$38/мес — за компанию или за приложение?** Предложение: за компанию (первое приложение
   открывает подписку, остальные внутренние — без доплаты).
2. **Публичные приложения: сколько стоят и кому?** Варианты: (a) бесплатны для установщиков,
   автор платит те же $38; (b) платит установщик по цене автора, платформа берёт комиссию;
   (c) бесплатны совсем (витрина как маркетинг). Предложение: (a) на старте.
3. **BYO-модели: каких провайдеров поддерживаем первыми?** Предложение: OpenAI-совместимый
   эндпоинт + Gemini + Anthropic (ключ компании), локальные — позже.
4. **Что происходит с установками при отклонении новой версии?** Предложение: работает предыдущая
   одобренная, автор правит и подаёт снова.
