## 1. Что такое «приложение» (решение владельца)

**Приложение = микросервис, код которого пишет бот.** Пользователь код НЕ видит и НЕ пишет: он
описывает боту задачу, смотрит результат в песочнице на синтетических данных, затем отправляет на
публикацию. Первая (отвергнутая) редакция этой спеки предлагала декларативный манифест без кода —
владелец выбрал полноценный микросервис, и это принципиально меняет контур безопасности (§5).

Приложение состоит из:

1. **Профиль (витрина)** — `app_key`, имя, логотип, категория, короткое описание, человекочитаемое
   длинное описание, контакт поддержки. Ложится на существующую `marketplace_apps`.
2. **Код** — сгенерированный ботом сервис (HTTP-хендлеры + логика). Хранится версиями, пользователю
   не показывается, модератору — по кнопке.
3. **Права доступа** — allowlist наших MCP-команд (каталог `agentSkillsMcpRegistry`,
   `chatgptMcpRead/WriteService`; MCP уже работает — используется приложением Avatars, при
   необходимости дорабатываем) **плюс** публичный REST API. Чтение и запись разрешены.
4. **Egress-allowlist** — список внешних доменов, куда приложению можно ходить. Пустой по умолчанию.
5. **Агент (опционально)** — персона + модель для сценариев с LLM; триггеры: вызов из чата,
   событие CRM (новый лид, работа закрыта), внешний MCP-клиент.
6. **Область** — `company` (только своя компания) или `public` (маркетплейс).

## 2. Жизненный цикл

```
draft → sandbox (синтетические данные) → submitted → in_review → published
                                                          └→ rejected → draft (+ причина)
```

- **Модерацию проходит ВСЁ**, включая внутренние приложения (решение владельца): любой запуск
  чужого кода в нашем контуре — через супер-админа.
- Правка опубликованного = новая версия на модерацию; у установщиков работает прошлая одобренная.
- Kill-switch у супер-админа: снятие с витрины + остановка контейнеров у всех установщиков.

## 3. Рантайм (решение: наша инфраструктура)

- **Контейнер на приложение**, без доступа к нашей сети и БД. Наружу — только через **шлюз**:
  MCP/REST в CRM (под RBAC установщика) и HTTP на домены из egress-allowlist. Всё остальное закрыто.
- **Скейл-ту-зеро**: без трафика контейнер спит, просыпается по запросу.
- **Компьют метрится и списывается** с кошелька компании (решение владельца) — отдельной строкой
  рядом с токенами.
- Песочница — тот же рантайм, но со **синтетическим тенантом**: сгенерированные лиды/работы/
  контакты/счета. Ни одного реального клиента.

## 4. Биллинг (решения владельца)

- **Платы за разработку приложений НЕТ** (владелец отменил идею $38/мес за внутренние).
- **Публичные приложения: платит установщик, платформа берёт комиссию.** Рельсы уже есть —
  Stripe Connect Standard + application fee (STRIPE-STANDARD-FEE-001); автору понадобится
  подключённый Connect-аккаунт для выплат.
- **Токены LLM** — с существующего кошелька, отдельной строкой расхода «App Studio».
- **Компьют** — оттуда же, по факту потребления.
- **BYO-модели пока не делаем** (решение владельца) — все приложения на наших моделях.

## 5. Безопасность (главный раздел — код чужой, права на запись есть)

1. **Изоляция**: контейнер без сетевого доступа к нашему периметру; секретов CRM внутри нет —
   вызовы идут через шлюз, который сам подставляет идентичность установщика.
2. **Потолок прав**: MCP/REST исполняются под RBAC установщика. Allowlist — потолок, а не выдача.
3. **Egress только по allowlist**, домены утверждаются на модерации; установщик видит их при
   установке («отправляет данные на …»).
4. **Автоматический сканер кода** перед модерацией: секреты, обращения к сети мимо шлюза, `eval`
   и динамическая загрузка, попытки чтения окружения/файловой системы, обфускация. Вердикт
   сканера — часть заявки; модератор может раскрыть код кнопкой.
5. **Автор публичного приложения не видит данные установщиков** — никогда, только статистика.
6. **Строить может только tenant_admin** (решение владельца).
7. **Лимиты**: CPU/RAM/время ответа/вызовы в минуту; превышение → приложение тормозится, владелец
   компании уведомляется.
8. **Описания и код — недоверенный текст**: трёхслойная модерация как у отзывов (ссылки →
   hard-reject, инъекции/мат → ручная проверка, fail-closed при сбое).

## 6. Данные (новые таблицы)

| Таблица | Назначение |
|---|---|
| `app_versions` | версия: `app_id`, `version`, `company_id`, `status`, `code_ref`, `manifest_json`, `scanner_report`, `submitted/reviewed_at/by`, `review_note` |
| `app_version_tools` | разрешённые MCP/REST-команды версии + scope |
| `app_egress_domains` | утверждённые внешние домены версии |
| `app_build_chats` | чат билдера на приложение (+ кнопка «новое приложение») |
| `app_build_messages` | **полный лог переписки**, хранится безусловно (решение владельца): роль, текст, модель, токены, tool-calls |
| `app_runtime_usage` | метрика компьюта и токенов на приложение → биллинг |
| `app_sandbox_runs` | прогоны в песочнице: вход, выход, ошибки |

## 7. UX

**Вход** — виджет обратной связи получает раздел **App Studio**: слева список приложений (каждое —
свой чат) + кнопка **New app**; в центре переписка с ботом; справа шторка с профилем приложения
(логотип, имя, описания, команды, домены) и кнопками `Test in sandbox` / `Submit for review`.
Статус версии — плашка вверху чата.

**Супер-админ** — вкладка **Apps**: очередь заявок, дифф к прошлой версии, запрошенные команды и
домены, отчёт сканера, полная переписка билдера, кнопка «показать код», Approve / Reject (+причина),
kill-switch по опубликованным.

## 8. Порядок работ

- **T1** — данные + модель версии + шлюз прав (без UI): allowlist команд, RBAC установщика, egress.
- **T2** — рантайм: контейнер на приложение, скейл-ту-зеро, лимиты, метрика компьюта.
- **T3** — песочница: генератор синтетического тенанта + прогон + показ результата.
- **T4** — чат-билдера: кодогенерация, хранение чатов/сообщений/версий, лог токенов.
- **T5** — UI App Studio в виджете.
- **T6** — модерация у супер-админа: очередь, дифф, сканер, код по кнопке, kill-switch.
- **T7** — публикация в маркетплейс + оплата установщиком через Stripe Connect с комиссией.

**Оценка**: это не одна задача, а мини-продукт. T1–T3 (шлюз, рантайм, песочница) — фундамент, без
которого остальное бессмысленно; T4–T5 дают видимую пользователю ценность; T6–T7 открывают маркетплейс.

## 9. Риски, которые я обязан назвать

- **Чужой код + права на запись + выход наружу** — это самая опасная поверхность в продукте.
  Смягчение: шлюз, allowlist, сканер, модерация всего, лимиты, kill-switch.
- **Стоимость**: контейнеры и кодогенерация — заметный расход; спасает скейл-ту-зеро и метрика.
- **Качество генерации**: бот будет писать нерабочий код чаще, чем хочется; песочница обязана
  показывать честные ошибки, а не «всё готово».
- **Модерация всего** делает владельца узким местом маркетплейса — стоит вернуться к этому,
  когда поток заявок вырастет.
