# APP-VIEW-001 — installed apps get a screen, a run history and a schedule

Status: proposed (architecture approved by the owner in outline, phasing open)
Depends on: APP-STUDIO-001 (§4 artefact/moderation), APP-GW-001, APP-RUN-001,
APP-TOOLS-001 (tool reference), APP-SANDBOX-001.

## 1. Why

An approved app today is a loaded gun with no trigger. The execution plumbing
exists — hash-pinned admission, short-lived run tokens, `/v1/runs/authorize`,
`/v1/runs/complete`, daily caps, wall-time auto-suspend — but nothing invokes a
live run, the returned value is discarded (`app_runs` keeps only `wall_ms`,
`result_bytes`, `error_code`), and the only place any output is visible is the
App Studio chat.

The owner's decisions, verbatim in intent:

- After publication an app is **standalone**. It has nothing to do with App
  Studio; App Studio only authors versions.
- An app must be able to build a **view** — a right-side panel whose content the
  app composes: charts, lists, blocks, and **tables**.
- A **schedule** is an installation setting: the app ships a suggested cadence,
  the tenant changes it — from frequent polling through daily, weekly, or a day
  of the month.
- Worked example the design must serve: an app that every day collects the parts
  to order from approved estimates.

## 2. The central decision: apps return data, never markup

App code is generated by a language model from an untrusted conversation. If an
app could return HTML or JavaScript, we would be pasting attacker-controllable
markup into our own origin — session theft, not a chart. So:

**An app returns a view document: a small, versioned JSON description of blocks.
The CRM renders it with its own trusted components.**

This buys four things at once: no XSS surface, automatic conformance to the
design canon, free mobile behaviour (the panel already becomes a bottom sheet),
and a forward-compatible contract — a new block type is a schema version bump,
not a redesign.

The rejected alternative is a sandboxed iframe with app-authored HTML under a
strict CSP. It grants more freedom and costs a permanent security surface, a
second design language inside the product, and its own escape-hatch review on
every version. Not worth it for charts and tables.

### 2.1 Document shape (view_version 1)

```jsonc
{
  "view_version": 1,
  "title": "Unpaid after visit",
  "subtitle": "12 jobs · $4,180 outstanding",
  "blocks": [ /* ordered, rendered top to bottom */ ]
}
```

Block types in v1:

| Type | Purpose | Payload |
|---|---|---|
| `stat_row` | 1–4 headline numbers | `items[]`: `label`, `value`, optional `tone`, `trend` |
| `chart` | `bar` or `line` | `series[]`: `label`, `value`; optional `format` |
| `table` | the workhorse | `columns[]`: `key`, `label`, `type`, `align`; `rows[]` |
| `list` | scannable records | `items[]`: `title`, `subtitle`, optional `badge`, `ref` |
| `text` | a sentence of context | `text` |
| `empty` | explicit "nothing found" | `text` |

Cell and value types: `text`, `number`, `currency`, `date`, `badge`, `entity`.

**`entity` is the only way an app links to anything.** It emits a reference —
`{"entity":"job","id":1219}` — and the CRM turns it into a link. An app can
never emit a URL. This closes redirect and data-exfiltration-by-link attacks in
one stroke, and it is why the block list has no `link` or `image` type.

### 2.2 Limits, enforced server-side

At most 64 blocks; 500 rows and 20 columns per table; 24 series per chart;
strings truncated at 500 characters with an explicit marker; 256 KB per
document. A document that violates the schema is a **failed run** with a precise
error shown to the app's author — never a partially rendered screen.

Validation runs in the **CRM**, not in the runner. The runner is the untrusted
side of the wall; the CRM is the authority. Same principle as execution
admission.

## 3. Storage

| Table | Holds | Why separate |
|---|---|---|
| `app_runs` (exists) | metering: `wall_ms`, `result_bytes`, `error_code`, timestamps | stays hot and narrow |
| `app_run_results` (new) | `run_id`, `company_id`, `installation_id`, `view_document jsonb`, `created_at` | different size class and retention |
| `app_installations.latest_run_id` (new column) | pointer to the newest successful result | opening the panel must be instant |

**Retention matters more than it looks.** A five-minute cadence is 288 runs per
day per installation; a one-minute cadence is 1,440. Keep the last 50 results
per installation and nothing older than 90 days, pruned by the same worker that
runs the schedules. Metering rows outlive results and stay cheap.

## 4. Execution: three triggers, one core

```
appExecutionService.run({ installationId, trigger, actorId })
  1. load installation + its approved, hash-pinned version   (exists)
  2. resolve the agent principal of the installer            (exists)
  3. POST runner /v1/run with a single-use run token         (exists)
  4. validate the returned value against view_version 1      (new)
  5. persist result + metering, move latest_run_id           (new)
  6. return the document
```

Triggers: `manual` (the Run button), `schedule` (the worker), and later `event`.
They differ only in who the actor is and which limits apply.

**One run in flight per installation.** Claimed with a row-level lock; a second
request while one is running returns the in-flight run rather than starting a
rival. Without this, a one-minute cadence on a slow app stacks runs until the
wall-time suspension fires — a self-inflicted outage.

## 5. Scheduling

`app_installation_schedules`: `installation_id`, `company_id`, `enabled`,
`cadence jsonb`, `next_run_at`, `last_run_at`, `last_status`, `failure_count`,
`suspended_reason`.

Cadence is a closed vocabulary, not raw cron — cron is unreadable to the person
setting it and lets a typo schedule a run every second:

```jsonc
{"kind":"every_minutes","n":15}
{"kind":"hourly","minute":5}
{"kind":"daily","at":"07:00"}
{"kind":"weekly","dow":1,"at":"07:00"}
{"kind":"monthly","dom":1,"at":"07:00"}
```

**Every cadence resolves in the company's timezone**, using the same bounds
helper that APP-TZ fixed — so "every morning at 7:00" means seven in the
morning where the company is, and the day of a DST change is 23 or 25 hours
long, not 24.

Worker: poll on a short interval, claim due rows with `FOR UPDATE SKIP LOCKED`,
respect the existing daily run cap and auto-suspend. A missed window is **run
once, never backfilled** — after a two-hour outage a per-minute app must not
fire 120 times. Three consecutive failures disable the schedule and raise a
task, because a silently dead schedule is worse than none.

The version manifest carries a `suggested_schedule`; installing applies it, and
the tenant edits it in the installation's settings.

**The cadence picker states the cost before the choice is made** (§10.1). A
minute-by-minute schedule is 1,440 runs a day and 43,800 a month per
installation; the screen says so in runs, data reads and compute time rather
than leaving the tenant to discover it on an invoice.

## 6. Where the user meets the app

Apps & integrations → an installed app card → **Open**. That opens the app's
own right-side panel (bottom sheet on mobile, per the overlay canon): the latest
stored result renders instantly, then refreshes. The footer carries *Run again*
and *Run history*; the schedule lives in the installation's settings.

App Studio does not appear anywhere in this flow.

## 7. Security invariants

1. The view document is data. The renderer is ours. No app-authored markup,
   script, style, or URL — ever.
2. An app runs with the **installer's** delegated permissions, but a **viewer**
   may hold fewer. A stored result is therefore gated on the viewer holding the
   app's declared business permissions; an app that declares none is visible to
   tenant admins only.
3. If the installer is disabled or loses a required permission, the schedule
   suspends. Fail closed — a scheduled robot must not outlive its authority.
4. Per-company caps: scheduled installations, runs per day (exists), wall time
   per run (exists), and stored results.
5. Every run keeps its audit row, including the failures.

## 8. What the parts-from-estimates app still needs

It cannot be built today: the catalog exposes Jobs and Tasks only. It needs
read tools for approved estimates and their line items — part name, quantity,
job and customer reference. That is a well-understood addition now that
descriptors carry documentation and the sandbox mirrors them, but it is its own
piece of work with its own permission (`estimates.view`) and fixtures.

## 9. Phasing

- **A — the screen.** View document, validation, renderer, *Run now*, history.
  Makes every already-approved app useful.
- **B — the clock.** Schedules, worker, installation settings.
- **C — the data.** Estimate and line-item read tools; the parts app becomes
  possible.
- **D — delivery.** Result into a task, a timeline note, an email. Needs write
  tools and a different permission model — deliberately last.

## 10. Decided by the owner

1. **No floor on cadence — every minute is available to every tenant**, but the
   product must be honest about the cost at the moment of choosing. Where the
   number can be computed it is shown outright (runs per day and per month,
   data reads per month, compute time per day); where it cannot, the trade-off
   is explained in plain language. The owner's words: give a forecast if we can
   compute one, otherwise explain it clearly. Never a silent expensive default.
2. **An app view opens for whoever holds the permissions the app declares** —
   a dispatcher opens a jobs digest, a technician does not. An app declaring no
   business permission stays admin-only.
